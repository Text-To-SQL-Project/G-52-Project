1. WHAT THE SYSTEM IS AND WHY IT EXISTS
================================================================================

THE PROBLEM

    A text-to-SQL system translates a natural-language question into SQL and
    runs it against a real database. Two things can go wrong, and they are
    different in kind.

    The first is unsafe: the generated SQL destroys or mutates data, or
    reaches rows the asker is not entitled to see. A language model asked to
    "clean up the attendance table" may produce a DELETE. A model handed a
    prompt-injected question may produce something worse.

    The second is subtler and more common: the SQL runs cleanly, returns a
    plausible table of numbers, and is wrong. It joined the wrong way, or
    filtered on the wrong column, and nothing about the output says so. The
    user has no way to tell a correct answer from a confident-looking
    incorrect one.

    Most published text-to-SQL work optimises execution accuracy and stops
    there. Accuracy alone does not tell a user which individual answer to
    trust.

THE DUAL PURPOSE

    This project is simultaneously two things, and several design decisions
    only make sense in light of the second.

    As an engineering deliverable it is a working, packaged application: a
    FastAPI backend, a React frontend, PostgreSQL, and Docker Compose, with
    per-user authentication and database-enforced row-level access control.
    It runs, it is demonstrable, and a non-technical evaluator can operate it.

    As a publishable contribution it is an evaluation artifact. The golden
    set, the scoring criteria, the calibration procedure and the findings log
    are the parts intended to survive review. This is why the repository
    contains a 1,512-line findings document that spends as much space on
    measurements that turned out to be wrong as on ones that held.

THE CLAIMED CONTRIBUTION

    Stated precisely, because overclaiming here would be the easiest way to
    lose a reviewer:

    1. Two independent safety layers, measured separately rather than
       together. A deterministic AST guardrail that never sees which model
       produced the SQL, and an LLM refusal layer that operates on the
       question. Reporting a single combined "safety rate" would hide which
       layer is doing the work; they are reported apart.

    2. Per-answer calibrated confidence, not just corpus-level accuracy. A
       five-signal fusion passed through isotonic regression fit on a
       question-level held-out split, reported with its Expected Calibration
       Error so the probability can be checked rather than trusted.

    3. A documented execution-match criterion with two scoring regimes,
       permissive and strict, both reported. The project's most transferable
       finding is that the choice between them changes conclusions, including
       one architectural decision that was made on the basis of the weaker
       one.

    4. Enforcement in the database rather than in generated SQL. Row-level
       access control is a PostgreSQL policy, not a predicate injected into
       the model's output, so it survives arbitrary query shape.

2. THE SCHEMA AND DATASET
================================================================================

THE college_erp SCHEMA

    A synthetic but realistically shaped college Enterprise Resource Planning
    database in PostgreSQL. Verified against the live database on 2026-09-14:

        Tables                          25
        Columns                        174
        Rows across all 25 tables  233,929

    The commonly quoted "~200K records" is consistent with the measured
    233,929; the precise figure is the one above.

    The schema spans six modules: core academic structure (departments,
    programs, academic_years, semesters, sections), people (students,
    faculty), teaching (subjects, subject_offerings,
    faculty_subject_assignments, student_section_mapping,
    student_enrollments), assessment (exam_types, exams, marks, attendance),
    finance (fee_categories, fee_structure, fee_payments), and auxiliary
    services (library_books, library_transactions, placement_companies,
    placement_drives, placement_applications, placement_offers).

    Two tables dominate the row count: attendance at 150,000 rows and marks
    at 40,000. That matters for the evaluation, because it makes join
    fan-out and aggregation errors produce plausible-looking wrong numbers
    rather than obvious ones.

    A separate application schema named app holds the system's own
    bookkeeping: query_history, users, and session_map. It is deliberately
    outside college_erp so that schema introspection, which resolves against
    college_erp only, can never surface credentials or audit rows to the
    model or to the Schema Explorer.

THE GOLDEN EVALUATION SET

    eval/golden_set.jsonl, 161 hand-authored and hand-verified questions.
    Composition verified by reading the file:

        Answerable                135
            simple_lookup           8
            aggregation            43
            multi_join             48
            date_filter            31
            ambiguous               5
        Unanswerable                8
        Adversarial                18
        ----------------------------------
        Total                     161

        Order-sensitive (ordered=true)   8

    Each record carries: id, question, gold_sql, answerable, adversarial,
    ordered, category. Unanswerable and adversarial cases have gold_sql=""
    by construction, since there is no result set to compare against; they
    are scored by refusal and clarification accuracy instead of execution
    match.

    The 18 adversarial cases include direct destructive requests, stacked
    injections, and prompt-injection phrasings. The 5 ambiguous cases are
    answerable in principle but underspecified, and exist to test the
    clarification path rather than the refusal path.

    The "135-question golden set" referred to elsewhere is the answerable
    subset. The full file is 161 questions and the safety metrics are
    computed over the adversarial and unanswerable cases that the 135
    excludes.

3. ARCHITECTURE, LAYER BY LAYER
================================================================================

REQUEST PIPELINE

    Question
      -> generation (LLM; may refuse)
      -> AST guardrail (may block; injects row cap)
      -> pre-execution detectors (schema alignment, back-translation)
      -> execution as a constrained role, inside a scoped transaction
      -> post-execution detectors (result sanity, multi-query agreement)
      -> confidence fusion + isotonic calibration
      -> response

LAYER ONE: THE LLM REFUSAL LAYER

    Where: app/generation/

    The model is instructed to decline rather than answer when a request is
    destructive or unanswerable from the schema. A refusal carries a kind,
    either "unsafe" or "ambiguous", and a reason. The prompt explicitly
    forbids the common evasion of substituting a harmless placeholder query
    instead of refusing outright.

    The two kinds map to two distinct response statuses, REFUSED and
    CLARIFICATION_NEEDED. Splitting them was a deliberate correction made on
    2026-08-26 (commit 36f370b); before that, an underspecified question and
    a destructive one produced the same outcome, which conflated a user
    problem with a safety event.

    What it catches: the great majority of destructive and out-of-scope
    requests, before anything is parsed or executed, and it is the only layer
    that can distinguish "I will not" from "I cannot".

    What it does not catch: anything reliably. It is a model following an
    instruction, and it can be argued out of a refusal. Nothing downstream
    assumes this layer ran.

LAYER TWO: THE AST GUARDRAIL

    Where: app/safety/guardrails.py

    Parses the generated SQL with sqlglot and decides on structure, never on
    keyword matching. Four named checks, a vocabulary frozen because it is
    part of the API contract:

        ddl_block        blocks Drop, Create, Alter, TruncateTable
        dml_block        blocks Insert, Update, Delete, Merge; also anything
                         that is not a read-only query (GRANT, CALL, COPY),
                         and state-changing function calls anywhere in the
                         AST
        row_limit        injects the default row cap when none is present
        subquery_depth   rejects nesting beyond the configured maximum

    Also rejected: multiple stacked statements, and SQL that fails to parse.

    THESE TWO LAYERS ARE SEPARATE DEFENCES AND ARE MEASURED SEPARATELY.
    This is a deliberate methodological choice, not a presentation detail.
    The guardrail block rate is computed over direct_sql cases, where
    adversarial SQL is submitted straight to the guardrail with no model in
    the path. sqlglot's AST analysis never sees which model produced the
    input, so the guardrail number is model-independent by construction and
    is identical for both providers. Refusal accuracy and clarification
    accuracy are computed separately over the LLM-mediated cases. A single
    merged "safety rate" would obscure which layer produced the outcome, and
    would make the guardrail look model-dependent when it is not.

THE FIVE CONFIDENCE SIGNALS

    Where: app/detection/

    1. sql_validity        Parses via sqlglot and passed the guardrail AST
                           checks. Deterministic. Measured AUROC 0.500 on
                           both providers under both scoring regimes: by the
                           time a query reaches scoring it has already
                           passed, so the signal is constant and carries no
                           discriminative information. It is retained
                           because it is free and because its absence would
                           be a silent failure.

    2. schema_alignment    Compares identifiers in the generated SQL against
                           the live schema. Deterministic, no LLM call.

    3. back_translation_match
                           Asks the model to translate the generated SQL back
                           into a question and compares it to the original.
                           One LLM call. Capped at 2 attempts as of commit
                           0752057; generation itself keeps the full 5-retry
                           budget.

    4. result_sanity       Inspects the returned rows for symptoms of a
                           subtly wrong query: empty result, a column that is
                           100% NULL, a NULL single-row aggregate, an
                           all-zero numeric column, hitting the row cap
                           exactly, duplicate rows under GROUP BY. Penalties
                           are module-level and tunable. Two issues force
                           status FAIL.

    5. multi_query_agreement
                           Generates an independent second query for the same
                           question and compares result sets. Disabled by
                           default (MULTI_QUERY_ENABLED=false) and dropped
                           from the weighted fusion. Section 5 below explains
                           why that decision is now known to be questionable.

    FUSION. A weighted mean over four signals, renormalised after
    multi_query_agreement was dropped:

        schema_alignment          0.35
        back_translation_match    0.29
        result_sanity             0.24
        sql_validity              0.12

    Any signal at FAIL forces the fused score down to FAIL_SCORE_CAP = 0.40.
    This is a hard safety invariant, re-applied after calibration rather than
    trusted to survive the calibration curve.

    A signal that was disabled rather than measured returns a neutral
    placeholder whose detail string carries the marker word "disabled". Such
    signals are excluded from both the weighted mean and the fail-override,
    so a switched-off detector does not drag the average toward 0.5. The
    frontend hides them rather than displaying a misleading 50%.

ISOTONIC CALIBRATION

    Where: app/detection/calibration.py, fit by eval/fit_calibration.py

    The weighted mean is a heuristic, not a probability. Isotonic regression
    maps it to P(correct), fit on a question-level 60/40 train/test split,
    seed 42. The split is question-level and never row-level, specifically to
    stop repeats of the same question leaking across the boundary.

    calibrated=True is reported only when a fitted artifact was actually
    loaded. A missing artifact degrades to the raw score with
    calibrated=False rather than silently pretending. As of the row-level
    security work, requests that run under per-user scoping also report
    calibrated=False, because they are fused over fewer signals than the
    calibrator was fit on.

PACKAGING

    FastAPI backend, React and TypeScript frontend built with Vite and
    Tailwind, PostgreSQL 16, orchestrated by Docker Compose. Five screens:
    Login, Workspace, History, Schema Explorer, Admin. The frontend container
    serves a pre-built static bundle through nginx, not a dev server, so
    source edits require an image rebuild.

5. EVALUATION METHODOLOGY AND ITS CORRECTIONS
================================================================================

THE EXECUTION-MATCH CRITERION

    Correctness is decided by executing both the gold SQL and the predicted
    SQL and comparing result sets. The project's criterion deliberately
    departs from the Spider/BIRD convention in four documented ways, all in
    the permissive direction:

    1. Column projection by name rather than exact column-set matching, with
       an AST-aware positional fallback for aggregate expressions.
    2. Multiset SUBSET matching rather than multiset equality for unordered
       cases.
    3. Gold's own display LIMIT stripped before comparison, for unordered
       cases.
    4. Order-sensitivity taken from an explicit per-case annotation rather
       than inferred from the presence of ORDER BY.

    A strict mode disabling all four exists and is reported alongside. Both
    numbers are published. Neither is "the" answer.

THE DOUBLE-CALIBRATION BUG

    fuse_confidence() unconditionally applies whatever isotonic calibrator is
    on disk. Every reconstruction of a "raw hand-tuned score" elsewhere in
    the codebase called fuse_confidence() to obtain it. It was not raw.
    fit_calibration.py's own printed label, "RAW hand-tuned score (no
    calibration)", was incorrect.

    Consequences, stated carefully because they differ by case. For Anthropic
    evaluating its own already-correctly-fit calibrator this was harmless: a
    redundant second isotonic pass whose main measurable effect is on
    AUROC's tie structure, not on ranking. For fitting a calibrator on a
    DIFFERENT provider's data it was actively wrong. The first Gemini
    calibration refit trained on scores that had already been passed through
    Anthropic's fitted curve, violating the requirement that a provider's
    calibration never reuse another provider's.

    The fix extracted compute_raw_score() from fuse_confidence(), containing
    the weighted mean and the fail cap with no calibrate() call.
    fuse_confidence() now calls it internally, so live application behaviour
    is provably unchanged; the full test suite passed unmodified.

    Validation: the fixed held-out evaluation reproduces the previously
    recorded pre-calibration baseline almost exactly, raw AUROC 0.552 and raw
    ECE 0.171 against a documented 0.557 and 0.172. Before the fix the
    identical call returned 0.564 and 0.114 to 0.121, silently pre-calibrated.

    app/detection/calibrator.joblib, the live production artifact, was never
    wrong. It had been fit on genuinely raw scores before the bug could
    apply. Only re-derivations since were affected.

PERMISSIVE TO STRICT, AND THE EX DROP

    Adding strict mode dropped execution accuracy substantially:

        Anthropic   0.714 permissive  ->  0.415 strict   (-0.299)
        Gemini      0.607 permissive  ->  0.363 strict   (-0.244)

    Neither number is wrong. They measure different things, and citing one
    without the other misrepresents capability in either direction. The
    project's position is that both must be reported together.

THE ABLATION INVERSION ON multi_query_agreement

    This is the most consequential correction in the project, because a
    production architecture decision rests on it.

    The original claim, documented in the repository before this
    investigation: dropping multi_query_agreement from the fused signal set
    improved AUROC by +0.074, from 0.575 to 0.649. On that basis the signal
    was removed from production and MULTI_QUERY_ENABLED defaults to false.

    Re-derived with the corrected raw scorer, under both label definitions,
    in-sample and held-out, on the same question-level 60/40 split:

        Anthropic (n=405, repeats=3)          in-sample   held-out
          Permissive, 5-signal (with MQ)        0.560       0.573
          Permissive, 4-signal (dropped)        0.625       0.552
          Delta (4 - 5)                        +0.065      -0.020
          Strict, 5-signal (with MQ)            0.772       0.804
          Strict, 4-signal (dropped)            0.717       0.729
          Delta (4 - 5)                        -0.055      -0.075

        Gemini (n=120, repeats=1)             in-sample   held-out
          Permissive, 5-signal (with MQ)        0.578       0.587
          Permissive, 4-signal (dropped)        0.543       0.563
          Delta (4 - 5)                        -0.034      -0.024
          Strict, 5-signal (with MQ)            0.816       0.772
          Strict, 4-signal (dropped)            0.742       0.795
          Delta (4 - 5)                        -0.074      +0.024

    Of the eight delta cells, exactly one reproduces the original
    justification: Anthropic, permissive, in-sample, +0.065. That is the
    single configuration the original decision was measured under. Under
    strict labels on both providers, and under held-out permissive on both
    providers, dropping the signal HURTS.

    Per-signal AUROC shows why. multi_query_agreement inverts harder than any
    other signal when the label definition changes:

        Anthropic   0.532 permissive -> 0.734 strict   (+0.202)
        Gemini      0.568 permissive -> 0.783 strict   (+0.215)

    On both providers it is the STRONGEST single signal under strict labels
    and among the WEAKEST under permissive. The inversion replicates across
    providers at nearly identical magnitude.

    THE MECHANISM, measured rather than theorised. Among the 405 Anthropic
    rows with a computable label, 155 are rows where the permissive and
    strict scorers disagree (145 of them permissive-says-correct,
    strict-says-incorrect) and 250 are rows where they agree.

        Anthropic          n     mean MQ score   status mix
          Disagreement    155        0.303       108 FAIL / 47 PASS  (70% FAIL)
          Agreement       250        0.632        92 FAIL / 158 PASS (63% PASS)

        Gemini             n     mean MQ score   status mix
          Disagreement     43        0.279        30 FAIL / 11 PASS / 2 WARN
          Agreement        77        0.656        24 FAIL / 48 PASS / 5 WARN

    The signal is disproportionately flagging exactly the rows where
    permissive scoring is being lenient about a genuine structural
    difference. Under permissive labels those correctly-flagged rows are
    mislabelled correct, so a low score there scores as a false alarm and
    drags measured AUROC down. Under strict labels the same rows are labelled
    incorrect and the identical score becomes a true positive. The signal's
    discrimination did not change. The label definition changed which of its
    correct calls counted as correct.

    The production default has NOT been reverted. The finding is documented
    and the decision is flagged as resting on one of eight measured
    configurations.

THE 0.649 DISCREPANCY, UNRESOLVED

    Ruled out: data drift (results.jsonl byte-identical per git history since
    the commit documenting 0.649), wrong weights (both the original
    5-signal and renormalised 4-signal weights confirmed against that
    commit's diff), and row-count mismatch (n=405 then and now).

    The double-calibration fix closed the gap to noise for held-out figures
    (0.552 reproduced against 0.557 documented; 0.171 against 0.172) but a
    residual 0.024 gap persists for the in-sample figure (0.625 against
    0.649). Suspected but unconfirmed: roc_auc_score tie-handling changed
    across sklearn versions and there is no record of which version was
    installed when 0.649 was first computed. sklearn==1.9.0 is pinned now.
    Rolling back was not attempted because it risks the current environment.

    For citation: use 0.625 in-sample and 0.552 held-out. Do not cite 0.649.

    RESOLVED 2026-09-15. The Admin endpoint at app/api/routes.py served
    fused_auroc=0.649 under a deliberate freeze. The freeze was lifted and
    the constant is now 0.625, with a comment at the site recording what it
    was and why it changed. eval/README.md's ablation table, which still
    presented 0.575 -> 0.649, was corrected to 0.560 -> 0.625 to match
    FINDINGS section 3. Every surface now agrees; 0.649 survives only as a
    superseded entry in the findings log and in this history.

    A second discrepancy, RESOLVED 2026-09-15 and unlike the one above it
    was fully explained rather than merely retired. README.md and the Admin
    endpoint reported held-out calibrated ECE as 0.118 against FINDINGS
    section 2's 0.121. Re-running the documented procedure gives 0.121 at
    n=162, matching the recorded split exactly, which rules out seed and
    eligibility. Reconstructing the pre-fix path -- push both halves through
    the production isotonic curve first, then fit again, which is what
    fuse_confidence() did before 4e9ac32 -- reproduces 0.117 on the RAW row.
    0.118 is that raw cell: never a calibrated result, but the ECE of
    already-calibrated scores mislabelled RAW by the script's own output.
    Cite 0.121 and the paired calibrated held-out AUROC 0.564; 0.118 and its
    paired 0.574 are superseded. Full derivation in FINDINGS section 14.

TWO FURTHER FAILURE MODES, IN THE LAYERS BELOW VERIFICATION (2026-09-15)

    The seven cases below are all in verification infrastructure. Two more
    were found on the same day, one layer down in each direction, and are
    written up as FINDINGS sections 15 and 16.

    A CORRECTLY-SCOPED ANSWER, INFLATED 39.8x, WITH NO SIGNAL (section 15).
    faculty1 asked "Which students are in my sections?" and received 1,000
    rows -- the guardrail's injected cap -- where the correct answer is 265
    students. The model self-joined student_section_mapping on section_id
    with no predicate on the second alias and no DISTINCT.

    Containment was perfect. Both aliases were independently filtered by
    Row Level Security: my_msm reached the same 8 sections a single-table
    read sees, out of 48 that exist, and the distinct result set is exactly
    the 265 of the teaching relation with zero of the 46
    department-but-not-taught students leaked. The generated SQL scoped
    nothing; the policy did all of it.

    The arithmetic is derived rather than asserted. Summing n-squared over
    the 8 visible sections gives exactly 10,541, matching the true row
    count; the degenerate unconstrained self-cross-join returns 70,225, and
    265 squared is 70,225 exactly.

    No detector fired, because result_sanity's duplicate check is gated on
    the SQL having BOTH an aggregate and a GROUP BY, and this query has
    neither. The only issue raised was row_cap_hit at penalty 0.10, whose
    message says more rows may exist beyond the cap -- true, and pointing
    the reader in exactly the wrong direction, since the answer is inflated
    rather than incomplete. The fused score came out around 0.90.

    This is the sharpest available illustration that CORRECT SCOPING IS NOT
    CORRECT ANSWERING: containment was perfect and the answer was useless.
    It is also the family's flattering direction -- a detector that stays
    silent is a false negative, but one that misses the defect, fires on
    something adjacent, and thereby raises apparent legitimacy is worse.

    Feasibility was measured rather than argued, because it decides paper
    framing. All 135 answerable gold_sql were executed unscoped; gold SQL
    is correct by construction, so anything that fires is a false positive.
    11.9% return some duplicate row, so a naive any-duplicate check is
    unusable, but a ratio check at 3.0x or above fires on one legitimate
    query (0.7%) and at 39.8x on none. The one persistent false positive is
    projection-induced rather than fan-out -- it drops identifying columns
    so distinct rows collapse -- which any future design must distinguish.
    Exactly one gold query hits the cap and its ratio is under 2.0, so cap
    AND high-ratio has zero false positives while either alone has one. The
    ratio needs no access to the suppressed set (39.8x scoped against 48.2x
    unscoped), so such a detector would not reintroduce the inference
    channel RLS closes. Recorded as a fixable gap and future work, not an
    inherent limitation. Nothing implemented.

    OVER-REFUSAL: A FAILURE MODE NO LAYER CAN SEE (section 16). A model
    declining a question it could have answered is read as success by every
    layer at once. The guardrail never sees SQL, so a refusal is its safest
    possible outcome. refusal_accuracy measures whether UNSAFE things are
    refused and has no term for an answerable thing wrongly refused;
    clarification_accuracy is blind the same way in the other direction. EX
    scores it incorrect but collapses it with generation error.
    result_sanity and confidence fusion never run. Not a check that passed
    for the wrong reason, but a success criterion that never included the
    failure.

    Measured on the banked results before any change, so the figures are a
    clean before-baseline:

        Anthropic  claude-sonnet-5, repeats=3   n=390   0 refusals   0.0%
        Gemini     flash-lite,      repeats=1   n=130  10 refusals   7.7%

    Anthropic's 40 declines land entirely on unanswerable (24) and
    adversarial (16) -- not one answerable question refused across 390
    records. Over-refusal is 19.6% of Gemini's permissive error and 12.0%
    of its strict error, so roughly a fifth of its permissive EX gap is
    refusal rather than generation error. The count is label-invariant,
    since a declined question has no SQL to execute; only its share moves.
    Gemini's permissive ceiling if every over-refusal became a correct
    answer is 0.607 -> 0.685.

    The ambiguous category is excluded, and the correction is recorded
    rather than applied silently. Those 5 questions carry answerable=true
    but exist to exercise the clarification path; declining them is correct
    and is what clarification_accuracy scores at 1.000. Counting them would
    penalise a model for behaviour another published metric rewards in the
    same run, and would have reported 15 over-refusals instead of 10.

    PROVIDER-SPECIFIC IS THE FINDING. Identical prompt, schema and golden
    set; only the model differs. Had both providers over-refused similarly,
    the honest reading would be that the schema representation forces it.
    One provider at zero rules that out -- the information is recoverable
    from the prompt as it stands, because one model recovers it. It is also
    visible ONLY because two providers were evaluated: on a single-provider
    evaluation this number is either 0.0% and invisible, or 7.7% and
    indistinguishable from generation error inside EX. That is a reportable
    argument for the methodology, independent of the finding itself.

    Root cause: app/schema/introspect.py collects all 43 foreign-key edges
    and populates is_foreign_key and references correctly;
    build_system_prompt() discards every one of them one function later,
    rendering only name and type. The built prompt contains no foreign key,
    primary key or reference wording -- verified by searching it. The model
    is told to use only the listed tables and columns, then shown a schema
    with every relationship stripped. Eight of the eleven over-refused
    questions are multi_join, which is where a missing relationship graph
    would bite.

    DECISION NOT TO RE-RUN, recorded as a decision rather than an omission.
    Anthropic is already at zero, so a prompt change cannot improve the
    primary baseline, only invalidate it. The FK graph is not orthogonal to
    the task, so unlike the row-scoping instruction it cannot be made
    conditional: a flag defaulting off during evaluation would guarantee
    that published EX never measures the shipped configuration, which is
    exactly the defect b091f6b fixed. And the upside is bounded -- 8 of the
    11 affected questions are intermittent, so +0.078 is an upper bound
    assuming every refusal becomes a correct answer. Spending the primary
    baseline's comparability to chase a bounded gain on the secondary
    provider is not a good trade.

    TOKEN-COUNT CORRECTION. The system prompt is 1,589 tokens (tiktoken
    cl100k_base), 2,050 with the five few-shot examples. A figure of ~2,391
    in informal use is wrong and should not propagate; it appears nowhere
    in the repository, and eval/README.md's 2011 per-call estimate agrees
    with the measurement to within 2%.

SEVEN CASES OF VERIFICATION INFRASTRUCTURE PASSING FOR THE WRONG REASON

    All seven are written up in eval/FINDINGS.md section 9 as of
    2026-09-15. They share a shape: the check was green, the green was
    honest about its own narrow assertion, and the gap was between what was
    asserted and what a reader would conclude had been verified.

    1. execution_match mislabelled correct answers as wrong. Name-based
       column projection produced a systematic one-directional labelling
       error on aggregate questions. Roughly 40% wrong labels in the sample
       that most distorts AUROC. Found by refusing to accept a below-chance
       metric and hand-auditing twenty extreme cases.

    2. The double-calibration bug. fit_calibration's "raw" scores were not
       raw. Found by tracing what the word "raw" actually meant in the call
       chain.

       This one has a second, larger half, written up in FINDINGS section
       14 and cross-referenced from section 9. The script printed a real
       number under the label "RAW hand-tuned score (no calibration)" when
       those scores had already been calibrated. The computation ran,
       nothing failed or warned, and the only false thing was the one thing
       the output asserted about itself. The figure -- 0.118 -- was read off
       that line into README.md, eval/README.md and the Admin endpoint,
       where it was served as a headline calibration result for nine days
       and through two documentation passes, one of which existed to correct
       stale figures.

       It is the only case in the set where the wrong value escaped the
       tooling and reached user-facing surfaces, and it outlived its own fix
       by nine days: the bug was fixed 2026-09-03, the number retired
       2026-09-15, because nothing connected "that function was wrong" to
       "therefore every figure it printed is suspect."

       A WRONG NUMBER IS MORE DURABLE THAN THE BUG THAT PRODUCED IT. Fixing
       the code does not retract its output. A fix is incomplete until every
       figure the broken computation produced has been traced to where it
       was published and either reproduced or retired.

    3. The read-only constraint was never exercised locally.
       get_readonly_engine() fell back to DATABASE_URL when unconfigured;
       that variable was unset on the host and readonly_app had never been
       created on the host database. Every host-side test run executed
       generated SQL AS A SUPERUSER. The five affected tests were not wrong
       about what they assert, but the read-only layer had no local coverage
       while appearing to sit behind a passing end-to-end test. Invisible
       because a privileged connection is indistinguishable from a
       constrained one on the happy path. Found by asking the live databases
       which role each component connects as, rather than inferring it from
       configuration.

    4. A count-based RLS probe. The first version of the section 10
       investigation gave the principal and the victim two rows each and
       compared count(*). A CTE attack shape returned 2 and was written up as
       "did not leak". It had leaked completely, returning the victim's two
       rows instead of the principal's. Caught only by re-running with
       unequal row counts and comparing row identity. This error was made
       while writing the section about checks passing for the wrong reason.

    5. eval/db_guard.py, caught prospectively rather than retrospectively.
       Row-level security, once enabled, would filter an eval run's rows
       without raising anything; execution accuracy would drift to a new
       plausible number with nothing in the output to say why. The guard
       aborts the run instead.

    6. That same guard was then a no-op for a day. assert_bypasses_rls()
       called is_immune(..., problem_tables=[]) as shorthand for "superuser
       or bypassrls", but an empty problem list means ownership-based
       immunity, so the call returned True for every connection and the
       function returned early every time. Its tests passed throughout:
       they exercise the pure decision function, which was always correct,
       and assert on source text, which was also correct. Nothing asked what
       the function DID. Fixed in 57611b2 with two behavioural tests, and the
       fix was verified by reintroducing the bug and confirming the new test
       fails. No published numbers were affected, because eval resolves to a
       superuser connection that was correctly admitted either way; the
       exposure was that a misconfiguration would not have been caught.

    7. psql -f /dev/stdin inside docker compose exec, applying a policy
       file. It printed SET, CREATE POLICY and GRANT and exited zero,
       having applied nothing from the file. Every part of that output was
       honest: statements really ran and really succeeded, but were read
       from somewhere other than the file handed over. ON_ERROR_STOP=1
       could not help, because there was no error -- there was no input.
       Found on 2026-09-15 when patched policies did not take effect; cost
       one debug cycle.

    The through-line, stated in FINDINGS section 9 because it generalises
    past all seven: VERIFY BY READING THE STATE BACK, NOT BY TRUSTING AN
    EXIT CODE. An exit code reports whether a process failed, not whether
    it did what was wanted, and the two diverge exactly when the input is
    wrong rather than the operation.

7. SECURITY AND AUTH WORK
================================================================================

    Full detail in docs/SECURITY_MODEL.md. Summarised here.

PER-USER AUTHENTICATION

    Replaced a single shared operator password with real accounts in
    app.users. Argon2id via argon2-cffi 25.1.0, with parameters pinned
    explicitly in app/auth.py rather than inherited from library defaults, so
    a dependency upgrade cannot silently move numbers cited in a paper:

        Algorithm     Argon2id
        time_cost     3 passes
        memory_cost   65536 KiB (64 MiB)
        parallelism   4 lanes
        hash length   32 bytes (256-bit tag)
        salt length   16 bytes (128-bit salt)

    This is RFC 9106's second recommended option. The first assumes 2 GiB of
    memory, which is unreasonable for a request handler. It also satisfies
    the OWASP Argon2id minimum. Measured verification cost: 77 to 112 ms,
    median 86 ms.

    A failed login verifies against a dummy hash so an unknown username costs
    the same as a real one. Unknown username, wrong password and deactivated
    account return an identical 401 with identical body and content-length,
    verified side by side.

SIGNED SESSION TOKENS AND PER-REQUEST ROLE RE-VALIDATION

    The token is HMAC-SHA256 signed, stdlib only, and carries exactly two
    claims: sub (user id) and exp. A test decodes a real token and asserts the
    claim set is exactly those two.

    ROLE AND is_active ARE NEVER TRUSTED FROM THE TOKEN. Both are re-read
    from the database on every request. Baking a role into a 12-hour token
    means a demotion does not take effect for up to 12 hours, and from the
    row-level security work onward that same role decides which rows are
    visible, so an authorisation gap widens into a data-exposure gap.

    Verified live against the running stack, same unexpired token throughout:
    deactivating a user mid-session produces 401 on the next request;
    reactivating restores 200; promoting a student to admin opens the admin
    route; demoting closes it again.

    Measured cost of the per-request lookup: median 4.7 ms, p95 5.6 ms,
    including connection checkout. Caching is therefore OFF by default. The
    setting exists but its TTL is documented as revocation latency, not a
    performance knob.

ROW-LEVEL SECURITY

    Eleven tables carry policies; fourteen shared reference tables
    deliberately carry none. The headline effect, same query, same live API
    path, same principal:

                                        before RLS    after RLS    admin
        SELECT count(*) FROM students        2000            1       2000
        SELECT count(*) FROM marks          40000           19      40000
        SELECT count(*) FROM attendance    150000           79     150000

    WHAT A FACULTY MEMBER SEES, AND WHY IT DIFFERS BY TABLE (commit 1d7f2fd)

    The original eleven policies gave only two tables a faculty branch, so a
    faculty member saw zero rows in marks, enrolments, section membership,
    fees, library loans and both placement tables. An ordinary question about
    their own students returned an empty result that looked like a broken
    query. The shapes were deliberate -- commit 5ef8f10 called seven of them
    "strictly own-rows" -- but nothing recorded whether faculty SHOULD reach
    that data. That question was answered explicitly on 2026-09-15.

    The principle now stated in docs/SECURITY_MODEL.md: teaching-relevant
    data is scoped by the TEACHING relation, institutional facts by
    DEPARTMENT, financial and placement data closed entirely.

        table                      faculty relation          faculty1
        --------------------------------------------------------------
        students                   department                     311
        attendance                 act performed (recorded)      2,410
        marks                      teaching, per mark              467
        student_section_mapping    teaching, per student           265
        faculty                    directory, any bound session    100
        faculty_subject_assignments  directory                     130
        fee_payments               none -- closed                    0
        library_transactions       none -- closed                    0
        placement_applications     none -- closed                    0
        placement_offers           none -- closed                    0
        student_enrollments        none -- closed by decision        0

    THREE DIFFERENT RELATIONS, ON PURPOSE. attendance is scoped by the act
    performed, students by department, marks and section mapping by teaching.
    That is intentional rather than drift: they answer three different
    questions. Whose attendance record is this -- the person who took it.
    Who is in my department -- an institutional fact independent of teaching.
    Whose marks may I read -- the ones I am responsible for assessing.

    marks is scoped PER MARK rather than per student, so a lecturer sees the
    marks they are responsible for and not the rest of that student's
    transcript in subjects they do not teach.

    "MY STUDENTS" IS APPROXIMATED, AND ERRS CLOSED. student_enrollments
    records enrolment in a programme and semester with no offering_id, so the
    schema contains no edge from a teaching assignment to an enrolled
    student. The teaching relation is reconstructed from marks instead -- a
    student the faculty member has assessed in an offering they teach.
    Consequence, accepted: a student who is taught but not yet examined is
    invisible to them.

    student_enrollments REMAINS CLOSED, BY DECISION, on two grounds. The
    schema cannot express a teaching relation there, per the missing edge
    above. And the realistic faculty question against that table is an
    institution-wide aggregate -- "how many students enrolled in each
    academic year?" -- which under ANY scoped policy returns a smaller number
    with nothing marking it partial. Closed, it returns zero rows, which is
    visibly wrong. A loud wrong answer beats a quiet one. This is also a
    documented limit of result_sanity: an empty result trips a penalty, a
    silently narrowed count trips nothing.

    WHY THE TESTS ASSERT IDENTITY HERE TOO. The department relation admits
    5,352 marks against the teaching relation's 467. A policy written against
    the wrong relation still returns "some rows, fewer than admin", which is
    exactly what a count assertion checks and passes. Only identity separates
    them. test_faculty_marks_are_not_the_department_relation pins the
    difference directly, and the isolation suite is now 82 marked tests, all
    of which refuse to run on a privileged connection -- verified
    behaviourally, 82 errors under the privileged condition against 82
    passing with the constrained role.

    CAUTION FOR ANY FIGURE CAPTION: student1 and student2 each see exactly 79
    attendance rows. That is a coincidence of the seeded data. A count
    comparison would pass even if the two students' records had been
    completely swapped, which is why every isolation test asserts on row
    identity rather than row count.

    THE IDENTITY-BINDING PROBLEM, AND WHY THE STANDARD PATTERN FAILED HERE

    The textbook PostgreSQL multi-tenant pattern stores the caller's identity
    in a session GUC and has policies read it with current_setting(). That
    assumes the SQL in the session does not touch the setting. In a
    text-to-SQL system the SQL is written by a language model, and it can:
    set_config() is an ordinary VOLATILE function, so a statement calling it
    is still a plain read-only SELECT that passes every guardrail.

    Measured against a live policy, nine of ten attack shapes bypassed it:
    subquery target list, CTE, CTE MATERIALIZED, scalar subquery, WHERE,
    LATERAL, window ORDER BY, UNION arm, top-level ORDER BY, CASE. Only
    EXISTS failed to leak, recorded as an observation rather than a safe
    shape. Two leak signatures appeared, and which one occurs depends on the
    query PLAN, meaning exploitability is a planner decision rather than a
    property of the SQL text.

    current_user is no escape: role is itself a writable GUC. A per-user
    database role reached by SET ROLE requires the pooled session user to
    hold membership in every such role, and a query can then switch freely
    among exactly those roles. That design hands over authentication rather
    than merely a value.

    THE CONTROL THAT REPLACED IT

    app.session_map, keyed on (pid, backend_start): the executing backend's
    process id and its start time. Neither is settable from SQL. The row is
    written by the privileged connection before the query begins; the
    executing role holds SELECT on that table and nothing else.

    The composite key exists because operating systems recycle process ids. A
    stale row keyed on pid alone would silently grant that identity to an
    unrelated backend, a wrong-user leak arriving through normal operation
    rather than through an attack. A test plants a stale row for the current
    pid with a different backend_start and asserts zero rows.

    Fail-closed by SQL semantics rather than by vigilance: the accessors
    return NULL when there is no valid mapping, so student_id = NULL is NULL
    rather than TRUE and the row is excluded. No mapping yields zero rows,
    never all rows, with no guard clause anyone could forget.

    Measured overhead on the real request path, 40 samples: 3.26 ms median
    total, of which 2.14 ms is the control and 1.12 ms is a deliberately
    retained redundant layer. The policy lookup compiles to an InitPlan at
    loops=1 against a 150,000-row table, so it does not scale with result
    size. Against a request dominated by a multi-second LLM call this is
    roughly 0.1% of a two-second generation.

    DEFENCE IN DEPTH, KEPT DELIBERATELY. The set_config denylist and the
    post-execution GUC re-assertion both remain, described in the code as
    redundant-by-design rather than load-bearing. They still catch one thing:
    a policy accidentally written against current_setting(), which is what
    every tutorial shows.

COLUMN-LEVEL RESTRICTIONS

    RLS filters rows and has no column dimension, and column privileges
    cannot vary per application user when every request executes as one
    database role. Three columns were therefore removed from the executing
    role's grants entirely:

        faculty.salary          compensation
        students.category       protected social attribute
        students.blood_group    health data

    The audit that found the latter two measured what each role could
    actually reach after RLS. Students were fine everywhere, seeing only
    their own row. A faculty member could read social category, blood group
    and date of birth for all 311 students in their department. Date of birth
    and contact details were deliberately LEFT readable; the line was drawn
    at protected attributes and health data rather than at "personal" in
    general. Faculty contact details remain visible to students as a staff
    directory.

    Each restricted column receives two treatments. It is omitted entirely
    from the generation prompt, so the model never learns it exists and never
    writes SQL that execution would refuse. It remains LISTED in the Schema
    Explorer, because structure is not data and an operator is entitled to
    know the column exists, but its sample values are suppressed.

    Consequence worth knowing: SELECT * now fails on students and faculty,
    because the wildcard expands to columns the role cannot read. This is
    mitigated at the cause, with the prompt instructing the model to list
    columns explicitly.

THE SCHEMA-BROWSER HOLE

    Documented as FINDINGS section 13 and worth restating because it
    generalises. Introspection runs on the OWNING connection, because reading
    catalogs completely requires it, and owners bypass RLS unconditionally.
    Two things it returned are data rather than structure: sample values
    (SELECT DISTINCT ... LIMIT 5) and row estimates (COUNT(*)). Both reached
    any authenticated user through GET /v1/schema.

    A policy audit cannot find this. pg_policies is complete and correct,
    testing the query path proves nothing because it is a different role on a
    different connection, and the endpoint is called "schema", which actively
    misleads.

    Now enforced: structure to everyone, data to admins only. Withheld row
    estimates are None rather than 0, since 0 would read as an empty table.

ADMIN-GATED BLOCKED-SQL VISIBILITY

    GET /v1/admin/blocked-queries serves the real, unredacted SQL for BLOCKED
    queries, across all sessions, gated by require_admin. Verified returning
    403 for a student and 401 unauthenticated. This exists so the blocked SQL
    is demonstrable to an operator without ever putting it back into a client
    response that a non-admin could see.

    The Admin tab is hidden for non-admins in the frontend, and that hiding
    is presentation only. The API enforces independently, and a stale client
    that still believes it is an admin receives a 403 and renders an honest
    "Administrator access required" state rather than a blank screen. This
    was verified in a real browser by demoting the account mid-session.

TELLING THE MODEL ABOUT SCOPING WITHOUT TELLING IT WHO

    A student asking "Show my attendance" received CLARIFICATION_NEEDED,
    because nothing in the prompt resolved "my". No SQL was produced, so RLS
    never got a chance to filter anything. A generation gap, not an
    enforcement gap.

    The instruction added states the SHAPE of the scoping and never the
    VALUE. Putting "you are student 32" in the prompt would invite the model
    to write WHERE student_id = 32, a predicate the MODEL chose, duplicating
    enforcement in the layer this project deliberately moved away from, and
    giving a prompt injection something to manipulate.

    It is conditional on row_scoped and never unconditional, so admin and
    eval requests receive a byte-identical prompt to the one that produced
    results.jsonl and results_gemini.jsonl. Three tests enforce that: one
    checks the unscoped prompt contains no fragment of the instruction's
    vocabulary, one checks the scoped prompt is the unscoped one plus exactly
    one line with nothing removed, and one parses the AST to confirm the
    append sits inside an if row_scoped branch. All three were verified to
    fail when the instruction is made unconditional.

    Verified live as student1: "Show my attendance" returns 79 rows and "What
    are my marks" returns 19, with no identity predicate in either generated
    query. An adversarial "show attendance for student 87" generates a query
    carrying that predicate, executes it, and RLS returns 0 rows.


================================================================================
8. KEY ENGINEERING LESSONS
================================================================================

    Stated as transferable findings.

    1. A CORRECTNESS LABEL IS A MODELLING CHOICE, NOT GROUND TRUTH.
       Every metric downstream of that choice inherits whatever bias it
       carries: accuracy, AUROC, calibration, ablation conclusions, and
       production architecture decisions. The defence is to compute the other
       definition and check whether the conclusion survives contact with it.
       This project changed a production default on evidence that held in one
       of eight measured configurations.

    2. ABSENCE OF A FAILING TEST IS NOT EVIDENCE THAT A CONTROL IS PRESENT.
       Six times, a check was green and honest about its own narrow assertion
       while the thing a reader would assume was verified was not. The common
       structure: the failure was invisible on the happy path, and none was
       found by running more tests. They were found by refusing to believe an
       implausible metric, by tracing what a word meant in a call chain, and
       by asking the live system a question its configuration could not
       answer.

    3. A SECURITY CONTROL THAT IS ONLY OBSERVABLE THROUGH WHAT IT PREVENTS
       GETS NO COVERAGE FROM TESTS THAT NEVER ATTEMPT THE PREVENTED THING.
       A privileged connection and a constrained one are indistinguishable on
       the happy path. Its presence has to be asserted directly, by
       interrogating the live connection's role, not inferred from feature
       tests being green.

    4. ASSERT ON IDENTITY, NEVER ON CARDINALITY.
       A count-based isolation check passed while a complete data leak had
       occurred, because the two parties happened to own the same number of
       rows. Test data should be constructed with unequal counts specifically
       so a cardinality match cannot be mistaken for a pass.

    5. IN AN LLM PIPELINE, THE SQL IS ATTACKER-INFLUENCED INPUT.
       Standard multi-tenant patterns assume the application controls the SQL
       in its own session. Here the SQL is model output. Any mechanism whose
       security depends on the session's SQL not doing something needs
       re-examining under that assumption, and nine of ten query shapes
       defeated the textbook pattern.

    6. PREFER A STRUCTURAL CONTROL TO A DENYLIST, AND SAY WHICH YOU HAVE.
       The denylist and the post-execution check are kept, and the code
       states in those words that they are redundant-by-design rather than
       load-bearing. Removing a layer the moment another one works would
       undercut a defence-in-depth argument; pretending a denylist is a
       boundary would be worse.

    7. FIX THE CAUSE, NOT THE SYMPTOM, WHEN THE SYMPTOM IS USER-VISIBLE.
       Restricted columns produced execution errors that looked like bugs.
       Withholding those columns from the model's schema stopped the errors
       being generated at all, which is better than rendering them politely.

    8. STRUCTURE IS NOT DATA, BUT A SAMPLE VALUE IS DATA WEARING STRUCTURE'S
       CLOTHES. Audit an introspection endpoint's response FIELDS, not its
       queries. Ask of each whether it could differ between two users of the
       same schema. If it could, it is data.

    9. AN EVALUATION HARNESS MUST NOT SILENTLY INHERIT PRODUCTION SECURITY.
       RLS does not make a restricted connection fail; it makes it return
       fewer rows. An eval run on a filtered connection produces
       plausible-looking numbers and no error. The guard that prevents this
       must itself be tested behaviourally, as lesson 2 was re-learned when
       that very guard was a no-op for a day.

   10. PUBLISH THE UNRESOLVED ONES.
       The 0.649 AUROC could not be reproduced and is documented as open
       rather than quietly replaced. A findings log that contains only
       successes is less credible and less useful than one that shows which
       numbers moved and why.

THE UNRESOLVED DESIGN DECISION: SURFACING BLOCKED SQL IN THE UI

    The current position is a compromise rather than a decision. Blocked SQL
    is withheld from every client response, because the raw SQL and parser
    errors embed real table and column names and returning them would undo
    the disclosure fix of 2026-08-31. It is available through
    GET /v1/admin/blocked-queries, admin-gated, unredacted, across all
    sessions.

    The tension that remains unresolved: the single most compelling thing to
    show an evaluator is the SQL that was blocked and why, and that is
    precisely what a non-admin user cannot see. During a demo the operator
    must switch to the admin account to show the very artifact that
    demonstrates the guardrail working. A student who triggers a block sees
    only a generic message and has no way to learn what was wrong with their
    question.

    Options considered and not chosen: returning a redacted form of the SQL
    with identifiers masked, which risks re-identification and adds a
    redaction layer to test; returning the blocked_reasons only, which is
    already done and is schema-safe but conveys little; and showing blocked
    SQL to its own author on the grounds that they wrote the question that
    produced it, which is arguably safe but has not been analysed.

    This is flagged as an open decision rather than a defect.

OTHER KNOWN OPEN ITEMS

    - Policy changes must be applied to BOTH PostgreSQL instances -- host
      5432, used by the test suite, and the container on 5433, used by the
      running API -- and verified separately by reading pg_policies on each.
      Applying to one leaves the other on the old policy with no error on
      either side. Documented in docs/SECURITY_MODEL.md.
    - (Closed 2026-09-15.) app/api/routes.py served fused_auroc=0.649 and
      held_out_ece=0.118 under a deliberate freeze. Both are retired; the
      Admin screen, README.md and FINDINGS now agree on every figure, and
      the live endpoint was verified returning 0.625 and 0.121 after an API
      rebuild. No surface presents a superseded value as current.
    - multi_query_agreement remains disabled in production on evidence that
      holds in one of eight measured configurations.
    - Gemini repeats=2 and 3 are partial (78 and 79 records) and unused.
      Completing them would remove the largest asymmetry in the results.
    - No confidence intervals or significance tests were computed for any
      reported metric.
    - A second isotonic calibrator fit on row-scoped runs has not been
      built, so row-scoped requests correctly report calibrated=False.
    - result_sanity cannot detect duplicate inflation outside a GROUP BY
      aggregate. A rows-to-distinct-rows ratio check is measured as
      feasible at under 1% false positives (FINDINGS section 15) and is
      proposed as future work. Nothing implemented.
    - The system prompt omits the foreign-key graph that introspection
      already collects, which is the suspected cause of Gemini's 7.7%
      over-refusal rate (FINDINGS section 16). The proposed fix is inline
      "-> table.column" annotation at +273 tokens, +17.2%. DELIBERATELY NOT
      APPLIED: Anthropic is at 0.0%, so the change cannot improve the
      primary baseline and would invalidate it, and reporting the fix would
      require a fresh re-run on both providers.
    - Gemini's over-refusal is mostly non-deterministic: of the 11 affected
      questions, 3 are refused on every repeat and 8 intermittently. Any
      future re-run must account for that before attributing a change to
      the prompt.
